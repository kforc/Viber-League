# 2026-10-09 — Viber League: adopting Viber Brawl's UI system

Goal this session: make Viber League read as the same family as Viber Brawl —
same arrangement, same consistency, same colour language — while keeping its own
football feel.

## Root cause #1: `#ui button` was silently outranking every button rule

`#ui button { pointer-events:auto; font-family:inherit; cursor:pointer; border:none; color:inherit }`
is specificity **(1,0,1)**. Every component class is (0,1,0). So `color:inherit`
beat `.primary-btn { color: var(--on-lime) }` and `border:none` beat
`.primary-btn { border: 4px solid var(--outline) }`.

Symptoms: the lime PLAY button rendered **cream text on lime** (effectively
invisible), and **no thick black outline rendered anywhere** — the entire chunky
design language the reference is built on was suppressed. `.primary-btn:disabled`
and every other `:disabled`/state colour was dead too.

Fix: split the rule. Keep the two non-clashing declarations on `#ui button`, and
move the clashing trio to **`:where(#ui) button`** — `:where()` contributes zero
specificity, so it resolves to (0,0,1) and components win while the `#ui` scoping
is preserved. `:where(#id) elem` is the idiom for "scope me, but stay weak".

Measured proof: before, the darkest pixel inside the PLAY button was `(224,248,5)`
(pure lime — no dark text at all). After, `(12,15,8)` = `--on-lime`, plus `(0,0,0)`
for the border.

## Root cause #2: `.special-label` is two different components

`ui/hud.ts` puts `<span class="special-label">SPECIAL</span>` inside the in-match
SPECIAL button. `ui/screens.ts` also uses `.special-label` for the player-detail
sheet's "SPECIAL MOVE" heading. The sheet's unscoped `.special-label { color:#d8b4fe }`
won the cascade for the button's child element, painting "SPECIAL" **light violet
on lime** — a matched rule on an element always beats a colour inherited from its
parent. Fixed by scoping to `.special-box .special-label` and rebranding it lime.

Wrote `/tmp/dupclass.py` to catch this class of bug generally: it parses every
`el('tag','class')` call, attributes each class to its enclosing function, and
reports classes created by more than one component. `.special-label` was the only
genuine cross-component collision; the rest (`.primary-btn`, `.ghost-btn`,
`.menu-opt`, `.ovr-badge` …) are intentional shared design-system classes.

## Root cause #3: HUD overlays were reserving layout height

`.banner` (the "KICK OFF" / "GOAL!" announcement) and `.setpiece-chip` were
normal flex children of `.hud-top-group`. **`opacity: 0` hides a box, it does not
remove it from layout** — so the invisible banner reserved ~69px and pushed the
whole bottom control bar (mentality row + SPECIAL + pause) **38px below the
bottom of a 390px landscape viewport**. Both are now `position: absolute`
overlays; the HUD reports `clipped=0 spill=0`.

## Corrections to the 2026-10-08 notes

**`Page.captureScreenshot` is NOT dead.** It worked this session in ~8s. The
previous "it hangs forever" conclusion was transient/environmental. What matters
is wrapping the send in a hard ~20-25s timeout so a hang degrades to "skipped"
instead of costing 46 minutes. The CLI path
(`chrome --headless --screenshot=…`) also still works.

**vitest SIGTERM (exit 137) is a V8 heap-reservation problem, not real OOM.**
System memory was 75% free while every test run died. The fix is a SMALL heap:
`NODE_OPTIONS="--max-old-space-size=384" node --max-semi-space-size=8 node_modules/vitest/vitest.mjs run <file> --pool=forks --poolOptions.forks.singleFork=true --no-file-parallelism`.
A large `--max-old-space-size` (2048/3072) makes it WORSE. Run the three files
one at a time. Result: **28/28 green** (12 match + 9 setpiece + 7 gameplay).

## Phase 2 — player profiles (username / team name / password at first run)

The request: *"make it possible that new users can set username and team name and
password at beginning so their profiles don't get lost."* The managed cloud
backend was unavailable, so the user chose **"Local profile now"** — this browser
only, no email, deliberately swappable for real accounts later.

### What was built

- **`src/app/profile.ts`** — the whole persistence surface, isolated on purpose so
  cloud accounts replace *this file* and not the screens. `loadProfile` /
  `saveProfile` / `clearProfile` / `createProfile` / `verifyPassword` /
  `storageAvailable` / `canHashPassword` / `PROFILE_LIMITS`. Storage key
  `viber-league:profile:v1`. The password is **never stored**: PBKDF2-SHA256 via
  `crypto.subtle`, 100 000 iterations, 16-byte random salt, 256-bit key, and a
  length-independent compare. A browser without `crypto.subtle` still works — the
  profile is simply saved without a password.
- **`src/sim/content.ts`** — `deriveShort(club)` (initials for multi-word, first
  three letters for one word, capped at 4, `'YOU'` if nothing survives) and
  `setPlayerClubIdentity(name, short)`. `CLUBS` holds the *same object reference*
  as `PLAYER_CLUB`, so mutating the fields is enough; call it before `createWorld`.
- **`src/ui/screens.ts`** — `renderOnboarding`, `renderSignIn`, `renderAccountSheet`,
  plus `renderTitle(root, onStart, opts?)` which now takes a manager name and
  renders the `.account-chip`.
- **`src/app/game.ts`** — `AppState` gained `'onboarding' | 'signin' | 'account'`.
  `bootstrap()` sends a returning player straight to the menu and a new one to
  onboarding. Dev hooks (`?hero`, `?autostart`) still win over the profile flow.

### Flow decisions worth remembering

- A **returning player is never asked again** — the profile is simply adopted at
  boot. The password exists for *signing back in after a sign-out*, not as a
  per-launch lock.
- Onboarding is **skipped entirely when storage is unavailable**: a sign-up form
  whose answers evaporate on reload is worse than no form.
- A profile saved **without** a password is opened by a single tap; the sign-in
  field is `disabled` rather than left as a box that swallows typing. The account
  sheet states `Password · Not set` outright.
- Sign-out only appears in the account sheet **when there is a password**.
- `renderOnboarding` gets no `onSignIn` — with no stored profile there is nothing
  to sign in to.

### Traps hit (each cost real time)

1. **`display: flex` beats `[hidden]`.** `.forgot-note` sets `display: flex`, and an
   author `display` declaration always outranks the UA's `[hidden] { display: none }`
   — so the panel never closed. Fixed with an explicit `.forgot-note[hidden]`.
2. **An untrusted `MouseEvent` does not run a submit button's default action.** The
   CDP harness clicks with synthetic events, so `click('.profile-submit')` silently
   did nothing on the onboarding form. Submit forms with `form.requestSubmit()`.
3. **`margin: auto` on the card, NOT `justify-content: center`.** A flex-centred
   child taller than its scroll container gets its top pushed past the scroll origin
   and cannot be scrolled back to. Auto margins centre when there is room and fall
   back to the top when there is not.
4. **`.screen > *` sets `position: relative`** — the account chip needed
   `.menu-screen > .account-chip` (0,2,0) to actually become absolute.
5. **Type errors**: `crypto.subtle.deriveBits` wants `salt: salt.buffer as ArrayBuffer`
   (`ArrayBufferLike` is not a `BufferSource`); `HTMLInputElement.autocomplete` is the
   `AutoFill` union, so `'nickname'` is invalid — use `'username'`.
6. **Chrome flags.** `--disable-gpu --in-process-gpu` kills WebGL and the app dies
   before rendering anything (`Error creating WebGL context`), which reads as "the
   UI is empty". The working set is
   `--headless=new --no-sandbox --enable-unsafe-swiftshader --use-gl=angle
   --use-angle=swiftshader`. Chrome also only survives inside the same Bash
   invocation that starts it.
